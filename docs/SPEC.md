# omabitrix — спецификация v0

Статус: v0.1 — ревью оракула учтено; TDD-контракт после гейта №0. Фокус: **задачи и чаты**; CRM не в скоупе. Тул личный.
Ресёрч: `docs/research/` — 02 (доступ, события, лимиты), 04 (задачи, чаты, упоминания, deep links).

## Одной фразой

Фоновый демон-компаньон для Omarchy: события задач и чатов Bitrix24 → нативные тосты и счётчики waybar, клик по тосту → карточка. Сам Б24 остаётся в браузере или официальном клиенте — мы не клиент, а мост «портал → десктоп».

## Не-цели v0

- Не клиент/обёртка Б24 (официальный Linux-клиент есть, AUR `bitrix24`).
- Не OAuth-приложение, не публичный сервер: только входящий вебхук (scope `task` + `im`).
- Не делаем: звонки/SIP, кнопки в уведомлениях, свой трей, мультипортал, CRM-события, мультиюзерность. Демон работает от одного юзера — владельца вебхука.

## UX

### Bar-плагин Omarchy shell (`omabitrix`)

QML-плагин `plugin/lenya.omabitrix/` → `~/.config/omarchy/plugins/lenya.omabitrix/`: `Omabitrix.qml` (BarWidget — иконка) + `manifest.json`.

Вид в баре: **одна иконка 󰭹 + бейдж непрочитанных** (чаты+уведы), always-visible; демону плохо/снапшот устарел >60 с → 󰅚 красным. Правый клик — портал, левый — TUI.


Обновление данных: `Timer` 5 с читает `snapshot.json` (в API для polling ходит только демон).

### Тосты

Отправка: `omarchy-notification-send --exec 'omarchy-launch-webapp <url>'` — клик по тосту открывает карточку, переживает рестарт shell.

| Событие | Источник | Уровень | Клик → |
|---|---|---|---|
| Личное сообщение | `im.v2.Event.get`, диалог user→user | normal, 8 с | `/online/?IM_DIALOG={userId}` |
| Упоминание `[USER={my_id}]` / `[USER=all]` в чате | `im.v2.Event.get` + парсинг `text` | normal, 8 с | `/online/?IM_DIALOG=chat{chatId}` |
| Сообщение в групповом чате без упоминания | — | нет тоста, только счётчик | — |
| Задача впервые попала в мой скоуп (создана или мне добавили роль, ≤7 дней) | дельта `tasks.task.list`: задачи нет в `known_tasks` | normal, 8 с | `/company/personal/user/{my}/tasks/task/view/{id}/` |
| Новый комментарий в моей задаче | `im.v2` событие чата `tasksTask` от другого автора | normal, 8 с | готовый `chat.entityLink.url` из события |
| Дедлайн ≤ 1 ч / просрочен | дедлайн-фильтры | normal, 12 с | карточка задачи |

Источник в тосте обязателен (юзер-фидбек): объект автора приходит прямо в payload (`data.user`, проверено живьём). Личка: Title = имя автора, Body = текст. Комментарий в задаче: Title = заголовок задачи, Body = «Автор: текст». Упоминание: Title = «Автор → чат».

Все тосты с явным `-t` (critical у dunst игнорирует таймаут и залипает — ревизия решения «critical для дедлайнов» по юзер-фидбеку).

- DND-окно в конфиге (ночь/выходные) глушит всё: просрочки копятся в панели, тосты не летят (`ponytail:` утренний summary — потом).
- `ponytail:` mute отдельных чатов и per-chat правила — потом.

## Архитектура

### Файлы

- Конфиг `~/.config/omabitrix/config.toml`: `portal`, `webhook_user`, `webhook_secret`, `user_id`, `portal_tz` (границы «сегодня»/«просрочено»; по умолчанию — из ответа задач: коробка отдаёт даты юзера +05:00 при сервере +03:00). ВАЖНО (проверено живьём): наивные строки фильтров портал трактует в СЕРВЕРНОЙ зоне — watermark дельты и границы «сегодня» демон пишет в серверской зоне, которую клиент узнаёт из `time.date_start` ответов, `poll_interval` (10 с), `dnd {start, end}`, `count_lines` (открытые линии в 💬, выкл по умолчанию), список игнорируемых чатов.
- State `~/.local/state/omabitrix/state.json` (запись атомарно: tmp + rename): `im_v2_offset`, `last_changed_date` (по ролям), `last_task_id`, `known_tasks` (множество ID моих задач — детект «впервые в скоупе»), `{task_id: new_comments_seen}`, `notified` (ключи `(kind, entity_id, day_bucket)` — идемпотентность тостов), снапшот счётчиков для waybar.

### Polling-цикл (раз в `poll_interval`, всё одним `batch` ≤ 50 команд; лимит 2 req/s соблюдён с запасом)

1. `im.v2.Event.get` (+ `offset`-подтверждение; при первом старте один раз `im.v2.Event.subscribe`; событие: `type`, `eventId`, `data.message`, `data.chat`). Сообщения из чатов задач (`chat.entityType=TASKS_TASK`) → «комментарий в задаче», клик — по готовому `chat.entityLink.url`. Комментарий НЕ меняет `CHANGED_DATE`, а `NEW_COMMENTS_COUNT` портал не фильтрует (обе проверки живые) → realtime через im.v2, catch-up после простоя — раз в час полный проход `tasks.task.list` по ролям с пагинацией (лимит 2 req/s соблюдается троттлингом клиента). Известный потолок: комментарий может тоститься дважды за день (realtime-ключ + catch-up day-key) — редкий случай после рестарта.
2. `im.counters.get` → 💬 и NOTIFY
3. `im.recent.list` `UNREAD_ONLY=Y` (LIMIT 200) → tooltip; дёргается каждый цикл (упрощение против «только при изменении счётчиков» — счётчики при живых чатах меняются почти всегда)
4. `tasks.task.list` дельта: `>CHANGED_DATE`, `order {"CHANGED_DATE":"desc"}`, три запроса по ролям (`RESPONSIBLE_ID` / `ACCOMPLICE` / `AUDITOR`) в одном batch — `::LOGIC OR` на коробке не работает (ошибка 1032, проверено на живой коробке), fallback — основной путь. Select: `ID, TITLE, STATUS, subStatus, DEADLINE, CHANGED_DATE, CREATED_DATE, NEW_COMMENTS_COUNT, COUNTERS`. Нюанс: в ответе поля camelCase, а даты — в таймзоне юзера (+05:00 на проверенной коробке при сервере +03:00)
5. `tasks.task.list` дедлайны: сегодня (`!STATUS:[5,6,7]`, границы в `portal_tz`) + просрочено (`STATUS=-1`, те же роли)

→ прогон через правила → тосты → перезапись state → сигнал waybar.

Catch-up после простоя: задачи и счётчики stateless (полный пересчёт по фильтрам); очередь `im.v2` живёт 24 ч — дыра в тостах сообщений при длинном простое допустима и задокументирована.

### Идемпотентность и пограничные случаи

- **Первый цикл — baseline без тостов:** состояние фиксируется, уведомления не летят (иначе — буря по всем просрочкам и непрочитанным после установки).
- **`notified`-map:** тост летит один раз на ключ `(kind, entity_id, day_bucket)`; просрочка тостится раз в сутки, а не каждые 10 секунд.
- **Cap на дельту:** после простоя дельта задач > 20 → один summary-тост («за время отсутствия: N изменений»), а не сотня тостов.
- **Комментарии и чаты задач дедупятся** (im.v2-событие vs рост `newCommentsCount`) — один тост на событие.

### Надёжность

- `flock` на state-файл: два инстанса демона на машине не воруют события. Известный потолок v0: очередь `im.v2` эксклюзивна на юзера — другой потребитель событий того же юзера (другой тул, второй ПК) будет конфликтовать.
- `QUERY_LIMIT_EXCEEDED` → пауза и повтор на следующем тике (10 с); сетевые ошибки — там же (упрощение против экспоненциального backoff).
- 401/истечение вебхука → waybar ⚠️, ретраи в journald, молчание запрещено.
- Запись state атомарная (tmp + rename), чтобы краш не рвал JSON.
- Логи в journald (`systemctl --user status omabitrix`).

### Технологии

Go-демон `omabitrixd`: один статический бинарь (~10 МБ), stdlib `net/http` + `encoding/json`, TOML — `BurntSushi/toml`, systemd user unit. UI — QML-плагин Omarchy shell (тема применяется сама). TUI v1 — bubbletea/lipgloss с палитрой темы. Упаковка: Makefile-установка; AUR — опционально.

Тесты (TDD): unit на правила тостов и парсеры (BB-код упоминаний, дельты, идемпотентность); цикл — против `httptest`-мока портала.

Установка: `omabitrix doctor` — проверяет вебхук, ставит systemd-юнит и плагин в `~/.config/omarchy/plugins/omabitrix/`, регистрирует виджет в `shell.json`.

## Гейт №0 (до кода, ~1 час)

Через входящий вебхук curl-ом:

1. `batch`-проба из 2 команд → закрывает тарифный вопрос.
2. `im.v2.Event.subscribe` + `im.v2.Event.get`.
3. `im.counters.get`, `im.recent.list UNREAD_ONLY=Y`.
4. `tasks.task.list`: `::LOGIC OR`-фильтр; дельта `>CHANGED_DATE` до/после добавления комментария; select `COUNTERS`.
5. `im.notify.get`: снять коды `notify_event` уведомлений об упоминании/назначении задачи (пригодится в v0.1).
6. Live-URL: открыть в браузере `/online/?IM_DIALOG=chat{id}` и страницу списка задач (клик ⏰) — снять фактические паттерны.
7. Написать комментарий в задачу → что прилетает в `im.v2.Event.get` и счётчики (от этого зависит правило дедупа комментариев).

**Результаты (коробочный портал, 2026-10-19):** ✅ batch/profile, im.v2 subscribe+get (`events/hasMore/nextOffset`), counters, recent, `STATUS=-1` (13), дельта `>CHANGED_DATE` (22/2 дня), дедлайн-сегодня `!STATUS:[5,6,7]` (59), `COUNTERS`/`newCommentsCount`, `im.notify.get` (`calendar/reminder`, `tasks/manage`), URL карточки задачи (открыт юзером), «комментарий → im.v2»: `ONIMV2MESSAGEADD`/`DELETE` с `chat.entityType=TASKS_TASK`, `chat.name` = заголовок задачи, **`chat.entityLink.url` = готовый URL карточки**; `im.message.add` в `chat{ID}` отображается в карточке как комментарий (подтверждено в UI), `im.message.delete` работает; ✅ `/online/?IM_DIALOG=chat{ID}` — открывает нужный чат (подтверждено юзером); ❌ `::LOGIC OR` (ошибка 1032) — работаем тремя запросами в batch; ⚠️ комментарий не меняет `CHANGED_DATE`, `commentsCount` = null, фильтр `NEW_COMMENTS_COUNT` игнорируется порталом (возвращает 0-комментные). Гейт закрыт: 7/7.

## v1: нативный quick-reply — РЕАЛИЗОВАН в QML-панели

Quick-reply сделан панелью плагина (см. bar-плагин выше), а не TUI: роднее к омарчи, не нужен отдельный процесс и сокет. История чата + ответ + пометка прочитанным работают через вебхук прямо из QML.

Осталось на потом (`ponytail:`): комментирование задач из панели (`task.commentitem.add` жив, но ограничен; `tasks.task.chat.message.send` — REST 3.0, проверить), вложения, реакции, звонки — для этого браузер (кнопка ↗). Отдельный TUI по SUPER+B — если QML-панели станет мало.

## Потолок v0 и путь апгрейда

- Задержка = интервал опроса (5–10 с). Истинный push — исходящий вебхук через туннель или OAuth-приложение + `event.offline.get` (админ + публичный HTTPS-callback) — позже.
- Один юзер на портал. Мультиюзер = OAuth-приложение — не нужно (тул личный).
- `ponytail:` CLI-флаги поверх конфига, mute-правила чатов, фильтры по группам задач — по мере надобности.
